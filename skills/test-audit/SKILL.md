# Test audit

Tests earn their maintenance cost when they protect observable behavior, a credible regression, or an independent contract. Use this skill as a gate before adding or changing tests, and as an evidence-first process for removing low-value tests and test-only production seams.

## Use

Use this skill when writing, changing, reviewing, or sweeping tests.

Do not remove a test because it is static, slow, or coupled to an implementation by appearance alone. Prove that a stronger boundary owns the contract or that no contract remains.

## Authoring gate

Before adding or changing a test, answer all four questions:

1. What observable behavior, invariant, or independent contract does it protect?
2. What credible regression makes it fail?
3. Why does existing coverage not already catch that failure? Each contract has one primary owner at the strongest boundary. A second layer needs its own distinct risk, such as a lifecycle or transport failure the primary owner cannot reach.
4. Does the test need a production export, flag, wrapper, or injection hook that no production caller needs? If yes, move the test to the real boundary instead.

A missing answer fails the gate. Prefer extending a table-driven case or shared fixture over adding a near-duplicate test. A bug regression test must fail on the pre-fix code for the intended reason and pass after the owner-boundary repair.

## Junk patterns

Reject a new test, or investigate an existing one, when it matches one of these patterns without an independent contract:

- assertion-free coverage probes, self-comparisons, or identity copiers;
- copied fixtures, inventories, manifests, or export lists;
- exact source, import, or string greps that do not protect an external byte, key, or path;
- private predicate or call-shape tests duplicated at a real boundary;
- repeated invocation of the same contract at another layer;
- provider-local replays of shared helpers;
- tests that exist only to preserve test-only exports, globals, or wrappers;
- dead production paths whose only callers are tests;
- expected values generated by the helper or renderer under test;
- mocks that implement the behavior being asserted;
- fixtures that supply the side effect, receipt, or ordering that production code should produce;
- negative controls that pass because an unrelated guard rejects the input;
- names or fixtures that promise more behavior than the test input exercises.

A test that breaks under behavior-preserving refactoring is asserting implementation. Rewrite it at the owning boundary before landing it.

## Audit workflow

1. Keep discovery read-only. Read the complete test, the production owner, entry points, callers, callees, sibling implementations, overlapping tests, relevant history, and repository instructions. Done when the proposed deletion has evidence, not a filename-level guess.
2. Record the candidate evidence: exact test and location, detectable failure, non-test callers of every covered seam, stronger remaining proof or why none is needed, relevant history, unlocked production or test-support deletion, risk, and focused validation command. Done when every field is known.
3. Choose one coherent owner-boundary batch. Remove obsolete test-only exports, globals, wrappers, and dead production paths with the test. Do not add replacement tests that restate the implementation. Done when the remaining owner proves the contract.
4. Run focused owner and sibling tests, repository-required checks, formatting, and `git diff --check`. Inspect the diff and classify production, tooling, test-support, and test changes separately. Done when every changed contract has current evidence.
5. For a broad campaign, audit one subsystem at a time. Write its boundaries and retention bar in the run record, then start the next subsystem only after the first coherent batch is committed. Done when campaign scope cannot turn speculative candidates into a deletion quota.

## Retention bar

Keep a test when it independently enforces a public API, protocol, configuration, migration, storage, security, platform, default, generated artifact, package, release, or architecture contract. Also keep call ordering when users observe it, credible regressions, and source inspection that is the cheapest independent guard for a user-facing key, byte, or path.

A retained test that fails on the baseline may show a product bug. Reproduce it and repair the production owner rather than deleting the test.

## Verification

Before ending the run, record the protected or removed contract, candidate evidence, tests and checks actually run, retained false positives and their contracts, production versus test-support versus test diff size, and commit or push state. A child audit report remains unverified until the coordinating run checks the integrated artifact.
